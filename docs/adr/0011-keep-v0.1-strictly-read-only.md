# ADR-0011: Keep `v0.1` Strictly Read-Only

- Status: Accepted
- Date: 2026-08-08

## Context

`v0.1` must establish whether a bounded Agent can gather useful Evidence and
produce a cautious Diagnosis. Kubernetes writes introduce a
different authorization problem: user intent, approval UX, target revalidation,
concurrency, durable audit, retry ambiguity, and post-operation verification.

Including dormant or hidden write code in `v0.1` would make the read-only claim
depend on UI visibility or prompt behavior instead of the executable
composition.

## Decision

`v0.1` will perform no Kubernetes write. Its composition contains no mutation
port, mutation adapter, write-capable Tool, generic Kubernetes request surface,
approval coordinator, Approval Dialog, or alternate CLI/TUI command that can
execute a recommendation.

The six model-visible Tools use only the bounded read behavior in the Scope.
The Resource Picker is also read-only and is not an action menu. Recommendations
in a Diagnosis are explicitly represented as not executed. A model statement
that an action occurred does not create Evidence or an execution result.

The Kubernetes adapter may depend on a library that contains write APIs, but no
write-capable client or method is exposed through a consumer port or wired into
the `v0.1` composition. Supported RBAC examples and test fixtures use only the
minimum read verbs and subresources required by the accepted Tools.

The separately admitted `v0.2` Deployment restart does not weaken this decision.
Its approval and executor code becomes reachable only in a `v0.2` composition
after all controls in ADR-0012 and ADR-0029 are present and verified.

## Consequences

Positive consequences:

- The MVP evaluates Evidence and Diagnosis without risking cluster mutation.
- Read-only is mechanically inspectable in ports, wiring, schemas, tests, and
  request recordings.
- Approval and mutation complexity cannot delay or silently enter `v0.1`.
- Recommendations remain clearly separated from observed and performed state.

Costs and constraints:

- Users must perform any chosen action outside KuPilot.
- KuPilot cannot verify the result of a user-performed recommendation as part of
  the same operation workflow.
- Code reuse with future write clients must not create an early generic escape
  hatch.

## Alternatives considered

- Shipping a disabled write executor was rejected because configuration, UI, or
  wiring mistakes could make it reachable and would expand the review surface.
- Allowing the model to emit kubectl commands for user confirmation was rejected
  because KuPilot would become a command generator without fixed semantics or
  safe parameterization.
- Adding a broad "are you sure" confirmation was rejected because it lacks a
  target-bound digest, TTL, revalidation, audit, and single-use state.
- Performing low-risk writes automatically was rejected because risk labels do
  not replace explicit authorization.

## Security and privacy impact

The absence of a write path limits model compromise and injection to bounded
read attempts that remain subject to scope, allowlist, projection, and budget
controls. It does not make all reads harmless; cluster data transfer and local
retention still require consent and minimization.

No prompt, model output, TUI text, configuration flag, or resumed Session can
activate a write in `v0.1`.

## Validation

Before `v0.1` release, deterministic checks must prove:

- The composition root constructs no approval or mutation implementation.
- Application, Agent, Tool, TUI, and CLI contracts expose no generic or write
  operation.
- Every recorded Kubernetes request from every command and Tool uses only the
  admitted read verbs, resources, Namespace, and subresources.
- Tool schemas contain no operation, patch, manifest, command, or approval
  field.
- The Diagnosis validator represents recommended actions as unexecuted and
  rejects unsupported execution claims.
- Dependency and import checks detect a second composition root or direct TUI,
  Agent, or Tool access to Kubernetes infrastructure.

A live cluster is not required; request-recording fakes are the release oracle.

## Revisit triggers

- Never for the `v0.1` version line. A write requires a later version and the
  separately Accepted approval and operation ADRs.
- A security finding exposes a path that can mutate despite the intended
  composition; release remains blocked until the path is removed.
