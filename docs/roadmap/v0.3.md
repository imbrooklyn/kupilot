# KuPilot v0.3 Quality and Maintainability Roadmap

## Purpose

`v0.3` strengthens the reliability, explainability, privacy lifecycle,
compatibility discipline, performance accountability, and release safety of
the admitted product. It does not start a feature-expansion cycle. The product
remains a local, single-process, single-user, Agent-first Kubernetes TUI with
the six fixed read-only Tools, the eight existing diagnostic categories, and
the single separately approved Deployment restart operation.

Work enters the release-critical set only when it has a stable source, a
sanitized deterministic reproduction, a measurable outcome, one owning layer,
a minimal file boundary, and an independent acceptance result. A broad theme or
future idea is not a work item.

## Conditional work

<!-- markdownlint-disable MD013 -->

| Candidate | Entry gate | Release effect | Mandatory limits |
| --- | --- | --- | --- |
| One additional read-only diagnostic category | A distinct sanitized diagnostic need demonstrates value, the eight admitted categories have no higher-priority defect, and a separate product, permission, privacy, budget, RBAC, Evidence, fixture, and maintenance review accepts it. | Not required for `v0.3`; omission cannot block release. | It requires an independent plan. It cannot be inserted into the fixed eight-category regression work or use a speculative Tool, Kind, relationship, or data source. |
| One dependency-group compatibility update | A repeatable supported-platform or security incompatibility identifies one concrete Go, Kubernetes, Eino, Charmbracelet, or SQLite dependency group. | Not required when the current supported matrix remains valid. | Upgrade one group at a time; preserve the Go minimum, license, CGO-free SQLite, contracts, race results, cross-builds, and performance budgets. |
| One future model provider | A later version accepts a separate ADR after maintenance-cost and compatibility review. | Outside the `v0.3` release condition. | At most one provider is admitted at a time; no simultaneous provider routing, fallback, or auto-detection. |

## Explicitly out

`v0.3` does not admit any of the following:

- A second Kubernetes write operation or broader patch, delete, apply, scale,
  rollback, exec, Helm, port-forward, or automatic remediation path.
- A resource browser, primary inventory table, resource tree, Dashboard, full
  YAML or raw-log viewer, live monitoring surface, shell, or kubectl wrapper.
- A seventh Tool, a new Kubernetes Kind or relationship, all-Namespace or
  cross-cluster diagnosis, Watch, informer, background scan, or concurrent
  AgentRuns as incidental maintenance work.
- Multiple simultaneous model providers, provider routing or fallback, MCP,
  RAG, retrievers, plugins, Multi-Agent orchestration, telemetry, or a hosted
  service.
- An unreviewed ninth diagnostic category as a release requirement.
- Production samples, raw logs, complete prompts, credentials, endpoints,
  cluster identifiers, or guessed issue narratives in fixtures or roadmap
  evidence.

## Release entry and exit rules

A release-critical item may start only after its reproduction uses synthetic or
fully generalized input, fits the named owning layer, and identifies the
smallest allowed files. Work stops if reproduction requires a real cluster,
real model, secret-bearing input, a broader permission, or an unadmitted product
surface.

`v0.3` is eligible for a release candidate only when every release-critical row
has its independent acceptance evidence, the eight diagnostic categories have
no regression, security and lifecycle canaries pass, migrations are repeatable,
there is no open P0/P1 finding, and supported cross-build plus offline release
checks pass. Conditional work never blocks that decision.
